# Profiler

Scripts for generating load and test resources for the EdgeCDN-X CoreDNS plugin.

## generate_zones.py

Generates `Zone` resources and, for each zone, a random number of `A`, `AAAA` and
`CNAME` `DNSEndpoint` records (`routingPolicy: Simple`). No dependencies beyond Python 3.
Use `--routing-policy Weighted` for A/AAAA-only WRR endpoints and endpoint-specific
generated Locations. In this mode record bounds apply to A/AAAA only (or their
combined count with `--total`); each endpoint selects only its own locations.
`--routing-policy Geolocation` also generates A/AAAA-only endpoints with dedicated
locations, GeoLookup attributes and node-group-specific selectors.

| Option | Default | Description |
| --- | --- | --- |
| `-z, --zones` | (required) | Number of zones to create |
| `--min-records` | `1` | Minimum records of each type per zone |
| `--max-records` | `10` | Maximum records of each type per zone |
| `--total` | | Apply min/max to total records per zone (random A/AAAA/CNAME split) |
| `--name-width` | `4` | Minimum zero-padded width of the zone number |
| `--max-targets` | `3` | Maximum targets per A/AAAA record |
| `-n, --namespace` | `edgecdnx` | Target namespace |
| `--zone-suffix` | `profiler.test` | Parent domain of generated zones |
| `--zone-prefix` | `zone` | Prefix of generated zone labels |
| `--ttl` | `60` | Record TTL |
| `--seed` | random | Seed for reproducible output |
| `-o, --output` | stdout | Write manifests to a file |
| `--apply` | | Apply via `kubectl apply -f -` |
| `--delete` | | Delete all resources generated by this script |
| `--context` | current | kubectl context |
| `--routing-policy` | `Simple` | `Simple`, `Weighted` or `Geolocation`; dynamic policies generate locations too |
| `--locations-per-endpoint` | Number of weights (`3`) | Dedicated locations generated for each dynamic endpoint |
| `--location-weights` | `1,2,3` | Weights cycled across each endpoint's locations; used weights must include a positive value |
| `--nodes-per-location` | `1` | Dual-stack nodes per generated location |
| `--routing-instance` | `edgecdnx` | Routing-instance label for generated locations |
| `--node-groups-per-location` | `4` | Geolocation groups; only the last matches the endpoint selector |
| `--geo-attribute` | `geoip/continent/code` | Geolocation metadata attribute |
| `--geo-values` | `EU,NA,AS` | Metadata values cycled across Geolocation locations |

Zones are named `zone-0001.profiler.test`, `zone-0002.profiler.test`, ... Records are named
`a-N`, `aaaa-N` and `cname-N` within each zone. A/AAAA targets use documentation IP ranges
(RFC 5737 / RFC 3849); CNAMEs point to an A record in the same zone.

All resources are labelled `profiler.edgecdnx.com/generated=true` for easy cleanup.

```sh
# Preview
./generate_zones.py --zones 5 --max-records 20 --seed 42

# Apply 100 zones with 10-50 records of each type per zone
./generate_zones.py --zones 100 --min-records 10 --max-records 50 --apply

# Generate WRR endpoints with six dedicated locations each (weights 70/20/10 repeated)
./generate_zones.py --zones 100 --routing-policy Weighted --total \
  --locations-per-endpoint 6 --location-weights 70,20,10 --nodes-per-location 2 --apply

# Clean up
./generate_zones.py --delete
```

`--delete` includes generated Locations. All cleanup commands target only
resources carrying the generated label in the selected namespace, but that scope
includes resources from other profiler runs. Do not run these benchmarks concurrently
in the same namespace. Location names include the endpoint name and location index.
Each Location has `zone: <Zone metadata.name>` and
`dnsendpoint: <DNSEndpoint metadata.name>` labels; the endpoint's
`spec.routeSelector.matchLabels` specifies both values. A and AAAA endpoints
receive distinct locations even within the same zone. Names used as label values
must fit Kubernetes' 63-character limit.
Generated nodes use documentation-only addresses and no explicit health status;
do not use them for production traffic. IPv4 addresses repeat after 254 nodes.

## test-simple.py

Measures how query latency changes as the number of zones and records grows. For each step
(default `100,1000,2000,5000,10000` zones, 10-20 random records per zone) it:

1. Applies only the zones that are new in this step. Generation is seeded, so each step adds
   to the previous one.
2. Picks a random 30% of all records and writes a dnsperf query file.
3. Waits until the plugin answers every sampled query with `NOERROR`.
4. Runs dnsperf at a fixed QPS (default 5000 for 30s) and appends a row to the CSV.

The CSV (`profile-results.csv` by default) contains the zone and record counts, apply and sync
times, dnsperf counters, achieved QPS, latency avg/min/max/stddev and p50/p90/p95/p99/p99.9 (ms),
and CoreDNS RSS. CoreDNS RSS is only recorded when the server runs locally. The query file and
raw dnsperf output for each step are kept in `profile-work/`.

Generated resources are deleted before and after the run (use `--keep` to keep them).
Requires `kubectl` and `dnsperf`.

```sh
# Defaults: local CoreDNS on 127.0.0.1:5553, namespace edgecdnx
./test-simple.py

# Custom steps, unthrottled dnsperf, more clients
./test-simple.py --steps 100,1000,5000 --qps 0 --clients 50 --duration 60 -o unthrottled.csv
```

Keep `--qps` fixed across runs you want to compare. Unthrottled runs mostly measure queueing
latency at saturation.

## test-wrr.py

Runs the same incremental scale/latency benchmark as `test-simple.py`, but creates
`Weighted` A/AAAA endpoints backed by dedicated locations for each endpoint.
Each step applies new locations before its new zones and endpoints. Existing
locations are not regenerated. Total locations equals endpoints multiplied by
`--locations-per-endpoint`, stressing selector lookup across many unrelated locations.
Both scripts use `profile_runner.py` for sampling, sync checks, dnsperf execution,
CSV reporting and cleanup.

```sh
./test-wrr.py --steps 100,1000,5000 --locations-per-endpoint 10 --location-weights 70,20,10 \
  --nodes-per-location 2 --qps 0 --clients 50 --duration 60
```

Default output is `wrr-results.csv`; raw query files and dnsperf logs go under
`profile-work/wrr/`. CSV adds `locations`, `locations_per_endpoint`, `location_weights` and
`nodes_per_location` to the Simple schema and works with `render-baseline.mjs`.
This measures performance, not returned-answer weight proportions. It requires
the DNS server to watch the selected namespace and serve generated location nodes;
use A/AAAA response mode to avoid timing CNAME response generation instead.
Cleanup includes generated Locations unless `--keep` is supplied. As with the
Simple benchmark, previously generated resources are deleted unless
`--no-cleanup-before` is supplied.
The benchmark measures the whole DNS serving path, including endpoint lookup,
target-cache lookup/rebuild, WRR scheduling and response creation, not isolated
DNSEndpoint map lookup. Use a new CSV output file if an existing WRR CSV has the
older shared-pool header.

## test-geo.py

Runs the incremental scale/latency benchmark with `Geolocation` A/AAAA endpoints.
Each endpoint has dedicated locations selected by location-level `zone` and
`dnsendpoint` labels plus a `profiler.edgecdnx.com/node-group=selected` label
present only on the last node group. Earlier groups are labelled `excluded`.
This exercises merged location/node-group matching on cache rebuilds, and
group-specific node selection on every query. `--nodes-per-location` means nodes
**per group** for this suite; only the matching group's nodes are eligible.
Location counts still equal endpoint counts multiplied by `--locations-per-endpoint`.

Each location has a default GeoLookup score of 1, a metadata attribute with weight
100, and one value cycled from `--geo-values`. Matching metadata adds a
location-index modifier. `--location-weights` supplies `geoLookup.weight` for
tie-breaking and must be in `[0, 1000]`, with a positive weight used per endpoint.
Each sampled record is queried twice: once with a random US IPv4 address and once
with a random EU IPv4 address carried in **EDNS0 Client Subnet (ECS, option 8)**.
Addresses use source prefix length `/32` and scope `/0`. Default source pools are
`24.0.0.0/24` (US/NA) and `80.156.0.0/24` (Germany/EU), checked against the local
GeoLite2-City database. These addresses are ECS metadata only: requests still go
to `--server`, and are not sent to or bound to the sampled public addresses.
The server needs `metadata` and `geoip { edns-subnet }` with a GeoIP database
covering these addresses. Without this configuration, default-score routing can
still return NOERROR, so sync success alone does not prove geographical routing.
GeoIP mappings can differ across databases; validate pools against the database
used by the target server. Custom metadata providers must derive the selected
attribute from ECS to exercise equivalent regional behavior.

| Geo suite option | Default | Description |
| --- | --- | --- |
| `--ecs-us-subnet` | `24.0.0.0/24` | Public IPv4 network to sample for US ECS clients |
| `--ecs-eu-subnet` | `80.156.0.0/24` | Public IPv4 network to sample for EU ECS clients |

Use `/32` pools for fixed client addresses. Custom pools must be correctly aligned
public IPv4 CIDRs; their geographical mapping is the caller's responsibility.

```sh
# Start small: 100 locations and 400 node groups across two endpoints.
python3 test-geo.py --steps 1 --min-records 2 --max-records 2 \
  --locations-per-endpoint 50 --node-groups-per-location 4 --nodes-per-location 2

# Increase total endpoints and unrelated locations while keeping load fixed.
python3 test-geo.py --steps 10,100,1000 --locations-per-endpoint 10 \
  --node-groups-per-location 8 --qps 5000 --duration 30

# Use a metadata attribute supplied by the server.
python3 test-geo.py --steps 10,100 --geo-attribute geoip/country/code --geo-values DE,US,JP

# Fixed ECS clients, useful for repeatable comparisons against a known database.
python3 test-geo.py --steps 10,100 --ecs-us-subnet 24.0.0.1/32 --ecs-eu-subnet 80.156.0.1/32
```

Default output is `geo-results.csv`; queries and raw logs go under `profile-work/geo/`.
CSV includes the dynamic-location columns plus `node_groups_per_location`,
`geo_attribute` and `geo_values`, which the SVG renderer displays as run context.
It also records `ecs_us_subnet` and `ecs_eu_subnet`. Use a new output CSV when
switching from the older GeoLookup schema without ECS columns.
Locations are applied before endpoints, and only new resources are applied at
each step. Cleanup includes generated Locations and uses the same generated-label
scope as the other suites. Do not run concurrently with them in the same namespace.

Ensure the server uses A/AAAA response mode, watches the chosen namespace and
routing instance, and has **no prefix route matching these endpoints**; prefix
routing takes precedence and would bypass GeoLookup. Disable any DNS response
cache for serving-path comparisons. Sync checks warm the sampled endpoint caches,
so measured latency is mainly warm GeoLookup scoring plus node selection and
response creation; it is not a cold-cache or cache-invalidation benchmark.
Geo suite query files use dnsperf's `-B` binary input mode: each DNS packet is
prefixed by a two-byte length and contains its own OPT/ECS record. This does not
switch the transport to TCP. Both sync checks and timed load use the same packets.
A companion `queries-N.bin.csv` records names, record types, region labels and
exact ECS addresses for auditing. Address selection is reproducible with `--seed`;
addresses are fixed when the generated input file repeats during a timed run,
not regenerated for each repetition. `sampled_queries` counts both regional variants.
The offered `--qps` is the combined US/EU load, not a per-region limit.
Repeat small runs with different group/location counts to compare those dimensions
without unintentionally generating millions of resources.

Offline regression tests (no cluster or dnsperf required):

```sh
python3 -m unittest discover -s . -p 'test_profiler.py'
```

An optional loopback wire test runs when dnsperf is installed and verifies that
it sends the binary packets' individual ECS addresses over UDP. It is skipped
otherwise; no cluster or external DNS service is contacted.

## render-baseline.mjs

Renders a CSV into a standalone SVG with achieved QPS, average query duration and maximum
query duration plotted against zone count on logarithmic axes. An exact-value table includes
zone and record counts. Requires Node.js 18 or newer; no package installation is needed.

Required CSV columns: `zones`, `records`, `achieved_qps`, `avg_latency_ms`, `max_latency_ms`.
Optional `duration_s`, `clients` and `qps_limit` columns supply run context.
Simple, shared-location WRR, per-endpoint WRR and GeoLookup output schemas are supported.
When present, total `locations` appears in the exact-value table and tooltips;
`locations_per_endpoint`, `location_weights` and `nodes_per_location` appear as
run context. Location counts must be nonnegative integers.
GeoLookup context also includes node groups per location and metadata attributes/values.
Rows are sorted by zone count, and invalid measurements cause an explicit error.
Visible headings and accessible SVG titles identify Simple routing, Weighted
Round Robin (WRR), or GeoLookup (with EDNS0 ECS when ECS columns are present).
GeoLookup/WRR columns take precedence over filename hints; names such as
`simple-baseline.csv`, `wrr-results.csv` and `geo-results.csv` identify older schemas.
Unrecognized sources use a generic DNS benchmark title.

Run from this directory:

```sh
node render-baseline.mjs simple-baseline.csv -o simple-baseline.svg
node render-baseline.mjs -i wrr-per-endpoint.csv
# Convert all CSV files in the current folder to same-basename SVG files
node render-baseline.mjs
node render-baseline.mjs --help
node --test render-baseline.test.mjs
```

Without `-o`, the SVG uses the input basename in the current directory.
Existing output files are overwritten.
With no input/output arguments, all CSV files in the current folder (not
subfolders) are converted. Invalid files are reported, valid files are still
converted, and any failure produces a nonzero exit status. `--output` requires
an input file; positional input and `--input`/`-i` are equivalent.
